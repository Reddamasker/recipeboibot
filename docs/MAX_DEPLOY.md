# Отдельный бот рецептов в MAX

Подготовлен отдельный контур для `id500912857935_bot`. Фактическая публикация и регистрация webhook фиксируются после выпуска; наличие этих файлов само по себе не означает, что бот уже запущен.

Контур: `/opt/recipeboibot-max`, контейнер `recipeboibot-max`, образ `recipeboibot-max-app`, SQLite в отдельном томе `recipeboibot-max_recipeboibot-max-data`. HTTP приложения доступен только серверу на `127.0.0.1:3089`; адрес Mini App — `https://recipeboibot-max.89-223-123-75.sslip.io`, webhook — `/api/max/webhook`. Исходники `src/public` общие с актуальным проектом. Окружение, пользовательские данные и ключ резервирования отдельные.

## Первый запуск

Локальный `.env.max.local` игнорируется Git и содержит `MAX_BOT_TOKEN` и, при необходимости, `MAX_WEBHOOK_SECRET`. Значения без кавычек. Секрет webhook — 32–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-`; если его нет, bootstrap генерирует новый на сервере. Не выводить значения в чат, терминал или журнал и не использовать их в аргументах команд.

```powershell
node scripts/deploy-max.js --setup-check
node scripts/deploy-max.js --setup
```

`--setup-check` — чтение и проверки: SSH, Docker, внешняя сеть `recipeboibot-v6`, свободный порт, nginx, certbot, ACME webroot, отсутствие прежнего MAX-контура. `--setup` повторяет проверки, требует чистый Git и коммит, запускает полный набор локальных тестов, передаёт архив коммита по SSH, создаёт отдельный контур и сертификат. Настройки других ботов не перезаписываются. На общей nginx меняется только отдельный новый vhost MAX с `nginx -t` перед reload.

На сервере по явному списку копируются только необходимые AI-ключ, модели и ограничения из действующего окружения основного контейнера с fallback на `.env.local`. Подключение OpenAI через существующий транзитный HTTP proxy настроено в отдельном compose. Telegram-токен, Robokassa, Директ, аналитические секреты и пользовательская БД основного бота не копируются. В MAX `BOT_PLATFORM=max`, `TELEGRAM_POLLING=false`; платёжные ключи отсутствуют, автопродление выключено. Trial запускается только пользователем средствами общей бизнес-логики.

## Последующие выпуски

Для повторной проверки онбординга владельцем предусмотрена `/test_reset` в личном MAX-чате. Доступ включается только для точного числового MAX ID через `MAX_TEST_RESET_USER_ID` в отдельном серверном `.env.local`; пустое или неверное значение закрывает команду. `TEST_CONTOUR` для этого включать не нужно. Команда показывает подтверждение и сбрасывает только аккаунт нажавшего владельца, включая рецепты, анкету, предпочтения, первый выбор и trial; общий AI-учёт сохраняется. `/start` после подтверждения начинает новый онбординг. Остальные пользователи MAX и основной Telegram доступа к сбросу не получают; прежний сброс в тестовом Telegram сохраняется.

```powershell
node scripts/deploy-max.js --check
node scripts/deploy-max.js --apply
```

Публикуется только коммит; секреты и база остаются на сервере. Все контуры используют общий Docker deploy lock, MAX дополнительно собственный lock. Перед заменой сохраняются исходники, предыдущий Docker-образ и согласованный SQLite snapshot, зашифрованный AES-256-CBC/PBKDF2 (200 000 итераций) отдельным `backups/backup.key`.

Серверные тесты запускаются без сети, рабочего окружения и томов данных. Затем проверяются HTTPS и локальные `/healthz`/`/readyz`, отказ webhook без секрета, отсутствие Telegram polling и чужих транспортных ключей, корректный платёжный режим, runtime revision, SHA-256 содержимого всех `src/public` и целостность SQLite. Итоговые метки — `DEPLOYED_REVISION`, `DEPLOYED_ARCHIVE_SHA256`, `DEPLOYED_SOURCE_SHA256`.

При неуспешном обновлении восстанавливаются только исходники/образ MAX, база и окружение сохраняются. При неуспешном первом запуске MAX-контейнер останавливается, созданный vhost снимается; отдельные ключ, окружение и том сохраняются для диагностики. Повторный `--setup` не затирает сохранившийся контур: сначала требуется восстановить незавершённый bootstrap по фактической причине ошибки. Скрипт не удаляет Docker-тома и не сбрасывает пользовательские данные или AI-квоту.

## Регистрация webhook

Регистрация подписки MAX выполняется отдельно после всех проверок публичного HTTPS, с тем же `MAX_WEBHOOK_SECRET`. Секрет нельзя размещать в URL. Не отправлять пробные события от имени реальных пользователей. `--setup` и `--apply` сами не изменяют внешнюю подписку MAX. После регистрации проверить реальный `/start`, кнопки, предпочтения, recipe flow, Mini App и голосовой ввод на MAX-аккаунте владельца; не объявлять интеграцию завершённой до этой проверки.

Проверенный официальный CA bundle `deploy/max-ca-bundle.pem` подключается только контейнеру MAX через read-only mount и `NODE_EXTRA_CA_CERTS=/app/deploy/max-ca-bundle.pem`. До запуска проверяется TLS и соответствие `/me` именно боту `id500912857935_bot`; ответ и токен в журнал не выводятся. Отключение TLS-проверки запрещено. Доверенный сертификат включается в коммит; секретные ключи сертификата не нужны приложению.

## Действующая оплата

6 октября по явному подтверждению владельца подключён существующий магазин Robokassa Myrecipies. Детали, проверенный runtime и резервы: [MAX_PAYMENTS_20261006.md](MAX_PAYMENTS_20261006.md). Первоначальный bootstrap выше по-прежнему создаёт MAX без платёжных ключей; подключение выполнено отдельно через `node scripts/deploy-max.js --apply --enable-payments` после штатного `--check`, проверок и резервирования. Обычные следующие `--apply` сохраняют платёжные настройки. При ошибке первоначального включения дополнительно восстанавливаются прежние окружение и compose MAX. Ключи магазина остаются только на сервере; счета MAX используют отдельный диапазон, подтверждения проверяются в своей базе.
