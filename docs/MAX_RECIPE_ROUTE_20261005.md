# Открытие готового рецепта в MAX — 5 октября 2026

## Причина и изменение

Владелец проверил живого бота: рецепт сформировался, но кнопка открыла общую страницу. MAX API подтвердил корректную кнопку `open_app` и payload с `recipe=dinner:<id>`. Сам рецепт сохранился и доступен своему пользователю: 13 ингредиентов, 6 шагов. Генерация при диагностике не повторялась.

В кабинете был зарегистрирован адрес `/?view=dinner`. В журнале за 17:51 UTC виден фактический запуск `/?view=dinner?WebAppStartParam=<payload>`: MAX добавил второй вопросительный знак. Вход и библиотека загружались с HTTP 200, но запрос конкретного рецепта не выполнялся. Код также запрещал применить стартовый payload, если URL уже содержал `view`.

В кабинете сохранён чистый адрес `https://recipeboibot-max.89-223-123-75.sslip.io/`, кнопка «Открыть» сохранена. После успешного серверного входа MAX navigation теперь берётся из подписанного `initData.start_param`, SDK или `WebAppStartParam` в query/hash. Поддержан и старый адрес с двумя вопросительными знаками. Навигация выбирает конкретную карточку поверх базового экрана; восстановление trial onboarding не перехватывает явный рецепт. Payload не выбирает аккаунт и не открывает произвольные URL, серверный контроль владельца рецепта сохранён. Telegram и публичные shared recipes сохраняют своё поведение.

VM-тест выполняет настоящий путь boot → проверка подписанного входа mock API → refresh → render → запрос конкретного рецепта. До исправления воспроизведены три падения. Покрыты адрес из живого журнала, обычный query/hash, raw SDK fallback, приоритет подписанного параметра, некорректные и повторные поля, отсутствие доступа, все seed IDs, trial onboarding, Telegram и public share. Новая генерация в этом тесте запрещена. Клиент `dinner-10.69`.
