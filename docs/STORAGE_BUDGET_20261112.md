# Хранение резервов и запас диска — 12 ноября 2026

## Причина

Проверка сервера в 08:34 UTC: диск 30 010 245 120 байт, занято 23 849 017 344,
свободно 6 102 667 264 (80%). Старое правило сохраняло по 30 зашифрованных,
но несжатых SQLite-копий. После роста базы оно перестало ограничивать общий объём:
основной бот — 5,30 GB, MAX — 3,03 GB, test — 0,25 GB; вместе с архивами
исходников и прочими резервами около 9,95 GB.

Контейнеры не забыли удалять: работали ровно три, остановленных не было.
Двенадцать образов соответствовали трём текущим и трём различным откатным
на каждый контур. Физическое хранилище containerd — около 8,57 GB;
логические размеры Docker cache и образов перекрываются и не суммируются.
Предыдущий контроль проверял количество файлов, но не их байтовый объём.

## Новая политика

- Общий `deploy/storage.py`, только стандартная библиотека Python и OpenSSL.
- Снимок через SQLite backup API с read-only подключением к живой базе.
  Gzip до AES-256-CBC/PBKDF2 (200 000 итераций), ключи контуров сохранены.
- До публикации каждого архива: расшифровка, распаковка, integrity_check,
  foreign_key_check, числа строк всех таблиц и SHA-256 всего исходного снимка.
  Архив и проверенный manifest публикуются атомарно, с fsync.
- Старые копии мигрируют с прежними параметрами шифрования (main 10 000,
  test/MAX 200 000). Исходный файл удаляется только после успешного полного
  восстановления нового архива и побайтового совпадения снимка.
- Последние три точки восстановления защищены. Дополнительно сохраняются
  последние точки каждого дня за 14 дней и каждой недели за 8 недель,
  в пределах бюджета: main 1536 MiB, MAX 1024 MiB, test 256 MiB.
  При нехватке бюджета удаляются самые старые дополнительные точки.
  Если три защищённые точки сами превышают бюджет, удаление прекращается
  с ошибкой; следующие создания блокируются до исправления бюджета.
- Ежедневный существующий backup timer создаёт и проверяет копии всех трёх
  контуров. Ошибка отдельного контура не мешает попытке остальных и остаётся
  видимой мониторингу. Возраст последней копии контролируется для всех трёх
  (30 часов), повторная проверка восстановления — не реже 24 часов.
- Часовая ротация сохраняет прежние ограничения Docker/исходников/логов,
  проверяет контрольные суммы архивов и лимиты. Служебные временные каталоги
  прерванных задач старше суток удаляются только под общим lock, без symlink.
- Предупреждение о диске с 75%, критическое — с 90%; общий аудит требует
  минимум 4 GiB свободного места. Обычный выпуск требует 6 GiB до загрузки
  архива и повторно под общим lock до резервирования и сборки.
  Создание/восстановление дополнительно проверяют собственный запас места;
  распаковка останавливается прежде, чем съест последние 256 MiB.

Это ограничивает управляемые резервы, но не обещает бесконечный объём для
растущих пользовательских данных. Данные не удаляются ради освобождения диска:
при росте базы сверх бюджета нужен пересмотр ёмкости с сохранением резервов.
Внешнее хранение по-прежнему не настроено; локальная копия не защищает от
полной потери сервера. Существующее предупреждение об этом сохранено.

## Служебный выпуск и восстановление

Штатные точки входа поддерживают `--check --storage-only`, затем
`--apply --storage-only`: сначала deploy-test.js, затем deploy.js и deploy-max.js.
Устанавливаются только семь явно разрешённых служебных файлов, с отдельным
архивом предыдущих инструментов и маркером STORAGE_DEPLOYED_REVISION.
src/public, окружения, Docker volumes и живые контейнеры не заменяются.
Идентификатор и время запуска контейнера проверяются до/после.

Восстановление в НОВЫЙ файл, никогда поверх живой базы:

```sh
python3 /opt/recipeboibot/deploy/storage.py restore production \
  recipes-YYYYMMDDTHHMMSSZ.sqlite.gz.enc /secure/new-restore.sqlite
```

Для test/MAX использовать соответствующий путь, contour и имя архива.
Команда проверяет байтовый хеш и все таблицы, отказывается перезаписывать файл.
Переход работающего приложения на восстановленную БД — отдельная аварийная
операция с остановкой единственного polling, сохранением нынешней базы и WAL.
Нельзя просто вернуть старый каталог deploy из архивов до этого исправления:
сжатые резервные копии требуют актуального storage.py и правил хранения.
