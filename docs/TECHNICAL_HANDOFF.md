# Техническая архитектура и handoff для реализации

Перед реализацией прочитать [CURRENT_DECISIONS.md](CURRENT_DECISIONS.md): этот документ фиксирует последующие решения пользователя и имеет приоритет. Реальный AI API обязателен; fake-адаптеры используются только в тестах.

Этот документ сохраняет исходный архитектурный план, а не перечень уже реализованных функций. MVP развёрнут 20 сентября 2026 на https://recipes.spas-sky.ru. Актуальное состояние, команды и проверки — в README и CURRENT_DECISIONS.md.

Фактические отличия: JavaScript/Node.js 24, встроенный SQLite, Telegram long polling, синхронная обработка без устойчивого worker, JSON-поля рецепта вместо нормализованных таблиц, без истории версий и экспорта. Поиск — AI-ранжирование последних 40 сохранённых рецептов владельца, без embeddings. Импорт URL использует JSON-LD/текст страницы; защищённые соцсети могут потребовать текст или скриншот. Квота резервируется до обращения к провайдеру: 40 в день, 80 всего, неуспешные вызовы учитываются. Нижеописанные очереди, индексы, метрики, повторы, полноценные source-adapters и учёт стоимости в долларах остаются планом, а не обещанием текущего MVP.

## 1. Архитектурный стиль

Рекомендуется модульный монолит с асинхронными worker-задачами. Микросервисы для MVP не нужны.

```text
Telegram Bot ─┐
              ├─ API / BFF ─ Auth ─ Recipe Application
Mini App ─────┘                  │
                                ├─ SQLite (closed MVP)
                                └─ Import pipeline
                                      ├─ Source adapters
                                      ├─ OCR adapter
                                      ├─ ASR adapter
                                      ├─ OpenAI Responses / transcription
                                      └─ Search indexing
```

## 2. Предпочтительный стек

Реализован компактный модульный монолит на Node.js 24 без внешних npm-зависимостей: встроенные HTTP/fetch, SQLite и статический Mini App. Для закрытого личного теста это сознательно заменяет более тяжёлую связку PostgreSQL/Redis/worker.

Вариант на TypeScript:

- backend и Telegram long polling: Node.js 24;
- Mini App: HTML/CSS/JavaScript, mobile-first;
- БД: встроенный SQLite с WAL;
- AI: OpenAI Responses API (`gpt-5.6-luna`) и Audio Transcriptions (`gpt-4o-mini-transcribe`);
- тесты: встроенный `node:test`.

Допустимый вариант на Python:

- backend: FastAPI;
- Telegram: aiogram;
- worker: Celery, Dramatiq или Arq;
- ORM: SQLAlchemy;
- frontend остаётся React/Next.js.

Если нет иных ограничений, для one-shot реализации предпочтителен единый TypeScript-стек.

## 3. Модули backend

### Identity

- Telegram user identity;
- проверка Mini App `initData`;
- внутренняя сущность пользователя;
- подготовка к дополнительным способам входа;
- удаление и экспорт данных.

### Recipes

- черновики и готовые рецепты;
- ингредиенты и шаги;
- версии;
- пользовательские изменения;
- теги;
- soft delete с последующей политикой физического удаления.

### Imports

- `ImportJob`;
- определение источника;
- адаптеры;
- загрузка и временные файлы;
- извлечение;
- нормализация;
- validation;
- повторные попытки;
- статусы и причины ошибок.

### Search

- полнотекстовый индекс;
- структурные фильтры;
- embeddings;
- разбор свободного запроса;
- ранжирование;
- строгая tenant-фильтрация по пользователю.

### AI Gateway

- реальные Responses, vision и Audio Transcriptions в продукте;
- строгая JSON Schema для рецепта, timeout и явные ошибки;
- дневной лимит и аудит usage;
- fake-реализации допустимы только в unit-тестах.

### Operations

- структурированные логи;
- метрики;
- трассировка фоновой задачи;
- health checks;
- административный просмотр неуспешных импортов;
- ручный повтор задачи без дублирования рецепта.

## 4. Ключевые сущности БД

Минимальный набор таблиц:

- `users`;
- `telegram_identities`;
- `recipes`;
- `recipe_ingredients`;
- `recipe_steps`;
- `recipe_sources`;
- `recipe_versions`;
- `import_jobs`;
- `import_artifacts`;
- `search_documents` или поля индекса в `recipes`;
- `provider_requests` для локального аудита демонстрационных операций;
- `audit_events`.

Во всех пользовательских запросах ownership проверяется сервером. Telegram ID не следует использовать как единственный primary key доменной модели.

## 5. Состояния задачи импорта

```text
received
  → fetching
  → extracting
  → normalizing
  → awaiting_review
  → saved

Любой промежуточный этап:
  → partial
  → retry_scheduled
  → failed
  → cancelled
```

Каждая задача имеет idempotency key. Повторная отправка одного webhook или повтор нажатия кнопки не должны создавать несколько задач без явного намерения пользователя.

## 6. Контракт нормализованного результата

Результат извлечения должен проходить строгую schema validation. Концептуальный формат:

```json
{
  "title": { "value": "Курица в соусе", "confidence": 0.96 },
  "servings": { "value": 4, "confidence": 0.61 },
  "ingredients": [
    {
      "raw": "2 куриных филе",
      "name": "куриное филе",
      "quantity": 2,
      "unit": "шт.",
      "confidence": 0.91
    }
  ],
  "steps": [
    { "position": 1, "text": "Нарезать курицу", "confidence": 0.88 }
  ],
  "warnings": ["Температура приготовления не указана"],
  "sourceEvidence": []
}
```

Нельзя автоматически преобразовывать низкую уверенность в достоверный факт. Порог отображения предупреждений должен быть конфигурируемым.

## 7. Стратегия импорта и расходов

Конвейер должен останавливаться сразу после получения достаточного результата:

1. Проверить дедупликацию по нормализованному URL и fingerprint источника.
2. Попробовать структурированный HTML.
3. Попробовать текст и metadata.
4. Использовать OCR или ASR только при недостатке данных.
5. Использовать vision только если более дешёвые способы не дали результата.
6. Отправить компактный материал в LLM для нормализации.

`UsageMeter` записывает:

- пользователя;
- задачу импорта;
- провайдера и модель;
- тип операции;
- количество токенов, секунд или страниц;
- оценочную и фактическую стоимость;
- latency;
- статус;
- повторный ли это вызов.

Квота списывается атомарно. Неуспешные технические повторы не должны многократно уменьшать пользовательский лимит.

## 8. AI-провайдеры и секреты

Текущий MVP обязательно требует реальный OpenAI API key. Личная подписка ChatGPT не подключается к backend.

В продукте подключены реальные OpenAI Responses API, vision и Audio Transcriptions. Ответы извлечения валидируются строгой JSON Schema; вызовы учитываются в `provider_requests`.

Актуальные переменные конфигурации:

```text
OPENAI_API_KEY=
OPENAI_TEXT_MODEL=gpt-5.6-luna
OPENAI_TRANSCRIBE_MODEL=gpt-4o-mini-transcribe
TELEGRAM_BOT_TOKEN=
INVITE_CODE=
AI_MAX_DAILY_REQUESTS=40
```

Реальные значения не коммитятся. В репозитории находится только `.env.example` без секретов. Unit-тесты не вызывают внешние API; отдельные smoke-скрипты проверяют реальные модели с малым расходом.

## 9. Платёжный контур

Платёжный контур полностью исключён из текущего MVP. Не создаются экран тарифа, webhook оплаты, подписки, entitlements и интеграция Tribute. Архитектурная возможность добавить эти модули позднее сохраняется за счёт модульного backend.

## 10. Безопасность и приватность

- Проверять подпись Telegram `initData` только на сервере.
- Не доверять `user_id`, присланному frontend-клиентом отдельно.
- Проверять ownership каждого рецепта и import job.
- Ограничивать тип и размер загрузок.
- Сканировать или изолировать пользовательские файлы.
- Удалять временные исходники по retention policy.
- Не журналировать ключи и пользовательский контент без необходимости.
- Шифровать соединения и данные резервных копий.
- Иметь политику удаления пользователя и его объектов.
- Подготовить Terms, Privacy Policy и Support до внешнего публичного пилота.

## 11. Минимальный UI

Экраны Mini App:

1. Onboarding.
2. Библиотека рецептов.
3. Состояние пустой библиотеки.
4. Поиск и фильтры.
5. Карточка рецепта.
6. Редактор черновика.
7. Режим готовки.
8. Статус и ошибка импорта.
9. Настройки, удаление данных и поддержка.

Карточка рецепта должна быть mobile-first и содержать источник, порции, время, ингредиенты, шаги, предупреждения и пользовательские заметки. Видео не должно быть обязательным для приготовления.

## 12. Тестовая стратегия

Обязательные автоматические тесты:

- проверка Telegram auth;
- tenant isolation;
- schema validation извлечения;
- state machine импорта;
- idempotency Telegram updates;
- поиск только внутри библиотеки пользователя;
- сохранение ручных исправлений;
- безопасная обработка неподдерживаемого URL;
- реальные OpenAI-вызовы отдельными малыми smoke-тестами.

Минимальный end-to-end сценарий:

```text
Telegram link
→ ImportJob
→ real OpenAI normalization
→ draft
→ Mini App edit
→ save
→ natural-language search
→ recipe card
```

## 13. Предлагаемый порядок реализации следующей задачи

1. Инициализировать монорепозиторий и локальную инфраструктуру.
2. Создать модель данных и миграции.
3. Реализовать Telegram auth и bot webhook.
4. Реализовать recipe CRUD и Mini App shell.
5. Реализовать очередь и state machine импорта.
6. Добавить текстовый и HTML-импорт.
7. Подключить OpenAI Responses, vision и Audio Transcriptions с лимитами.
8. Добавить OCR и выбранные source adapters.
9. Реализовать поиск.
10. Добавить observability, security checks и end-to-end тест.
11. Подготовить инструкции запуска и checklist демонстрации.

## 14. Definition of Done следующей задачи

One-shot MVP должен поставляться как запускаемый проект, а не набор несвязанных экранов. Минимально ожидаются:

- воспроизводимый локальный запуск;
- `.env.example` без секретов;
- миграции БД;
- seed или fixtures;
- бот и Mini App;
- фоновые worker-задачи;
- реальные text, vision и ASR-адаптеры;
- unit и integration tests;
- один end-to-end happy path;
- README с командами запуска;
- список осознанно оставшихся ограничений.

Реальные корпоративные ключи, платёжные реквизиты и юридические документы не требуются для визуального MVP. Они подключаются отдельной задачей перед внешним пилотом и не могут быть придуманы в ходе реализации.
