## Использование дашборда

- Откройте `https://dishfinder.ru/dashboard` и введите пароль дашборда.
- Верхние карточки показывают всех достигших этапа. График показывает последовательную цепочку запуск → результат → триал → оплата; справа — конверсии. Выбор блюда из подборки показан отдельно и необязателен для триала.
- «Создать рекламную ссылку» добавляет размещение. Название и короткий код, например `kanal_oct`, вводятся в форме. Повторное создание с тем же кодом возвращает прежнее размещение.
- «Скопировать ссылку» в таблице — ссылка для рекламной публикации.
- Фильтр «Размещение» или «Открыть воронку» — новая рекламная когорта конкретной ссылки.
- «Внести статистику» — общие показы и охват площадки. Охват необязателен. Повторный ввод заменяет итог, не прибавляет его.

Для каждого размещения используйте отдельную ссылку. При работе на основном домене она имеет вид `https://dishfinder.ru/go/kanal_oct`; технический домен APP_URL обслуживает ту же базу. Тестовый дашборд выдаёт ссылку своего домена. Команды отчёта/создания рекламы в Telegram удалены до публикации после уточнения владельца.

## Что считается

Показы и уникальный охват берутся из рекламного кабинета или статистики публикации. Автоматической интеграции с площадкой нет: источник рекламы пока не указан владельцем. Неизвестные значения обозначены «нет данных»; ноль не подставляется. Общий охват разных размещений не складывается, поскольку аудитории пересекаются.

Переход — GET к зарегистрированной ссылке `/go/:slug`, за которым сервер выдаёт 302 в Telegram. HEAD, известные preview-боты и prefetch не учитываются. Открытие Telegram и просмотр чата отдельно подтвердить нельзя. Повторные переходы считаются запросами; это не уникальные люди. Неизвестные сканеры могут увеличивать счётчик. Исторические клики до подключения не восстанавливаются. IP, User-Agent и cookie для этой аналитики не сохраняются.

Каждый переход получает случайный token в параметре `/start ad_<token>`. Первый зарегистрированный `/start` связывает пользователя с размещением; повторные команды не меняют источник. Ранее запущенные аккаунты считаются повторными посетителями и не входят в новую рекламную когорту. Общий отчёт включает исторические `is_allowed=1`, но не выдумывает дату их первого Start. Конверсия переход → запуск использует число различных переходов с новым Start, чтобы пересылка одной Telegram-ссылки нескольким людям не давала больше 100%.

Первый рецепт — успешный готовый рецепт в коллекции (включая позднее архивированные), конкретный рецепт в `recipe_suggestions`, успешный `first_recipe_results` либо фактически показанная рекомендация ужина. Черновики, ошибки и незавершённая генерация не учитываются. Считается получение результата, не факт приготовления. Для новых first_recipe_results сохраняется completed_at; старые данные используют доступное время начала.

Триал — серверная запись `user_trials`; повторная активация и истёкший trial не меняют факт прохождения этапа.

Оплата — `payment_orders.status='paid'`, `paid_at` и `is_test=0`. Новые initial/recurring заказы сохраняют режим при создании. Заказы тестового контура и режима провайдера помечаются `is_test=1`; старые заказы без отметки (`NULL`) показываются отдельно и не объявляются настоящими продажами. Промодоступ, ручная подписка и mock_payments не считаются оплатой. Повторный callback и повторная покупка не увеличивают число оплативших пользователей.

Последовательная цепочка требует прохождения этапов по времени: Start → результат подбора → триал → оплата. Результатом может быть рецепт по конкретному запросу или показанные варианты ужина. Принятие варианта необязательно: «Выбрали рецепт» показывает только явный выбор из подборки. Верхние карточки показывают всех достигших каждого этапа, включая тех, кто пропустил trial или активировал его до результата. Проценты внутренних этапов относятся к предыдущему этапу цепочки; подбор → выбор блюда считается отдельно. Общий Start включает органику, поэтому процент из рекламных переходов доступен только отдельному размещению.

Аккаунт владельца и private-test-профили исключены из пользовательских чисел. Удаление аккаунта каскадно удаляет персональную атрибуцию; анонимные переходы сохраняются. Отчёт относится к сохранившимся аккаунтам, а не к пожизненному числу всех удалённых пользователей.

## Технический доступ и проверка

`node src/admin-funnel.js [код]` выводит JSON. Дашборд использует `/api/dashboard/funnel?campaign=код`, `/api/dashboard/campaigns` и `/api/dashboard/stats`. Данные требуют серверной сессии после входа по паролю; Telegram для входа не нужен.

`node src/admin-funnel-access.js --create` создаёт новый случайный пароль, сохраняет scrypt-хеш в БД и завершает прежние сессии. Пароль выводится только этой доверенной CLI-командой. Cookie сессии HttpOnly, SameSite=Strict, Secure в production; срок семь суток. В БД хранятся SHA-256-хеши session token, не сами токены. Запись требует специального заголовка и проверки Origin; вход ограничен по частоте. API и пароль не публикуются в Git. Пароли контуров независимы.

Локальный предпросмотр: `node scripts/preview-funnel.js`, затем `http://127.0.0.1:3091/dashboard`. Отдельная `data/funnel-preview.sqlite`, пометка «Демо данные», никакого polling или AI; доступ в игнорируемом `data/funnel-preview-access.json`. Это вымышленные числа исключительно для проверки интерфейса. Скрипт в production-образ не входит.

Аддитивные миграции: acquisition_campaigns, acquisition_clicks, acquisition_starts, acquisition_metadata, funnel_credentials, funnel_sessions; payment_orders.is_test; first_recipe_results.completed_at. Пользовательские данные, сроки доступа и AI-квота не сбрасываются; модели, интерфейс пейволла и его несогласованный макет не меняются.

Автотесты проверяют атрибуцию, повторы, последовательность, подписанный платёжный callback, ошибки генерации, отдельный подсчёт тестовых/неизвестных оплат, запрет доступа без пароля, сессии/истечение/смену пароля, защиту от чужого Origin, формы размещений, preview-запросы и удаление аккаунта.
