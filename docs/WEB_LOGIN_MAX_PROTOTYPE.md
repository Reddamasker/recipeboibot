## Граница прототипа

Скрытая страница `/web-login/prototype` создаёт запрос на пять минут. В исходном браузере и в боте показан одинаковый код. Только явно настроенный владелец может подтвердить запрос. После подтверждения исходный браузер получает отдельную сессию на 30 минут. Она подтверждает работу механизма, но не авторизует `/api/me`, рецепты, подписки, платежи или дашборд. Telegram и MAX не объединяются в один аккаунт.

Настройки включаются только вместе: `WEB_LOGIN_PROTOTYPE_ENABLED=true`, `WEB_LOGIN_OWNER_MAX_ID` (настоящий числовой MAX ID владельца), `WEB_LOGIN_ORIGIN` (точный HTTPS origin без завершающего слеша). Платформа — только MAX. Нет ID по умолчанию. Отключение флага закрывает все маршруты прототипа. Включение в рабочем MAX требует решения владельца о контуре; ранее согласованные тестовые изменения дизайна не являются разрешением перенести их в основной MAX.

## Проверки и защита

Независимые случайные секреты браузера, бота и сессии; в SQLite хранятся их SHA-256 хеши. Токен deep link заменяется внутренней ссылкой до записи в MAX inbox. Вход привязан к владельцу и конкретному сообщению с кнопками. Одноразовое завершение транзакционно. Куки HttpOnly, SameSite=Strict, Secure и host-only для HTTPS; сессия не передаётся в URL или storage. POST требует точного Origin и отдельного заголовка. Результат нельзя встраивать во frame. Есть лимиты запросов и срок хранения диагностики семь дней.

Код сравнения снижает риск случайного подтверждения, но не делает механизм устойчивым к фишингу: пользователь должен сам начать вход на доверенном сайте. Подтверждение чужой пересланной ссылки недопустимо. Прототип не обещает вход в другой браузер: после MAX нужно вернуться именно в исходную вкладку Safari/Chrome. На десктопе открывается клиент/веб MAX; QR в этой версии нет.

## Локально

`node scripts/preview-web-login.js` — отдельная тестовая БД `.tmp/web-login-preview.sqlite`, только loopback, без воркеров и настоящих ключей. Ссылка на фиктивного бота не предназначена для реального подтверждения. Интеграционные тесты имитируют только транспорт MAX; реальное прохождение с телефона проверяется отдельно после согласования контура.

## Диагностика

Внутренний прототип не смешивается с продуктовой воронкой и рекламной конверсией. Серверный источник — состояния запроса: создан, сообщение доставлено (не прочитано), подтверждён/отклонён, потреблён браузером, истёк. Клиентские события — видимый экран, нажатие входа, видимый результат, перечислимая ошибка и потеря очереди. Повторы используют прежний ID; аналитика не блокирует вход. Тексты, URL, секреты и MAX ID не включаются в агрегат.

`GET /api/dashboard/web-login-prototype` требует существующую независимую авторизацию дашборда. При выключенном прототипе возвращает `null`, а не нулевые метрики. Отчёт содержит начало сбора, окно семь дней, внутренний источник MAX, этапы и p50/p95 времени доставки, решения и завершения. Доля завершения считается среди запросов, срок которых уже закончился; активные запросы отдельно. Основной MAX bridge не расширяется: эта диагностика не является метрикой общего продукта. До реального включения локальные данные не выдаются за сбор в рабочем контуре.

## Проверка владельцем после включения

Открыть согласованный HTTPS URL в Safari/Chrome → начать вход → открыть MAX → сверить код и подтвердить → вернуться в исходную вкладку → увидеть подтверждение → обновить страницу → выйти. Отдельно проверить отказ, истечение пяти минут и повторное нажатие старой кнопки. Зафиксировать фактические состояния, куки и внутренние агрегаты без копирования секретов. До этого шага сквозная проверка MAX остаётся незавершённой.
